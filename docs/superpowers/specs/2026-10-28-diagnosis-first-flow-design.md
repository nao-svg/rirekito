# リレキト for 営業職 — 診断先行フロー・職務経歴書・面談導線 設計書

日付: 2026-10-28
前提の設計書: `docs/superpowers/specs/2026-10-09-sales-pivot-design.md`（営業職版。6タイプ診断・提携先一覧などはこれを引き継ぐ）

## 背景・なぜ作り直すか

CA（加藤さん）から本番アプリへのフィードバックを受けた（2026-10-21・10-27）。

- 「5分で完成・スマホ完結・無料」はどこも言っていて、パッとしない。
- SNSから軽い気持ちで来た人に、最初に履歴書の基本情報（氏名・住所など）を入力させるのは負担が大きく、離脱する。
- 自己診断（選択式）だけで作る自己PRに、架空の数字（成約率・売上1位など）が本人の実績のように入ってしまう。
- 連絡先は、診断結果を見たあと本人が「履歴書を作りたい」「相談したい」と思ったタイミングで聞くのが自然。
- 強みを引き出すときに実際に聞いている質問は「熱中したこと」「仕事に対する不満」「その不満に対して自分で行動したこと」。
- 面談前に助かる情報は「現在の職業」と「希望の職業」。
- 予約したくなる相談は「求人相談」。

## 誰のためか（ペルソナ）

- **中心となる人**：「学歴がないから雇ってもらえない」と感じている20代。チェーン飲食店などで働き、フリーターに近い働き方をしている。年収は300万円程度。
- **届け方**：SNSの動画で「学歴がなくても大丈夫！営業マンやってみよう」と呼びかけ、アプリに来てもらう。
- **本人の気持ち**：「フリーターだった自分が、スーツを着てビジネスマンとしてやっていけるのか」が一番の不安。

## 成功の形

- ユーザーにとっての成功：**「これなら応募できそう」と思える履歴書と職務経歴書が手に入ること**。
- 事業にとっての成功：「プロと一緒に仕上げる」を選んだ人が BEPRIDE の面談につながること。これが「1面談いくら」の収益になる。

## ゴール / やらないこと / 失敗とみなすこと

**ゴール**
- 動画から来た人が、何も入力せずに（選ぶだけで）診断結果までたどり着ける。
- 本人の言葉をもとに、架空の数字を含まない自己PRと職務経歴書ができる。
- 「プロと一緒に仕上げる」を選んだ人の申し込みが、BEPRIDE に確実に届く。

**やらないこと（今回の範囲外）**
- 看護師向け・施工管理向けなど、別ペルソナの入口
- マイページ・ログイン
- BEPRIDE のシステムとの自動連携（API など）
- 求人の掲載

**失敗とみなすこと（動いても失敗）**
- 本人が書いていない数字や実績が、自己PRや職務経歴書に入る。
- 診断で「あなたは営業に向いていない」と突き放す。
- 本人の同意なしに BEPRIDE へ情報が渡る。または、同意した内容と違う情報が渡る。
- 最初の画面で、名前・住所などの入力を求める。

## 全体の流れ（決定済み）

画面イメージ: `.superpowers/brainstorm/8291-1793151895/content/flow-v1.html`（ローカルのみ）

1. **入口（トップ）**：「フリーターだった私でも、営業マンになれる？」のように、学歴・職歴が関係ないことを前面に出す。「無料で診断してみる」ボタン。「登録なしで結果まで見られます」と書く。
2. **診断（選ぶだけ）**：今の10問（6タイプ判定・配点は均等化済み）に、経験を聞く質問を1〜2問足す（例：「接客のアルバイトや仕事をしたことはある？」）。経験の質問はタイプ判定の配点には使わない。
3. **診断結果**：「あなたは営業マン、いける！」と背中を押す。理由は経験の答えから作る（例：接客経験あり →「毎日お客さんと話してきた経験は、営業で一番大事なコミュニケーション力そのもの」）。経験がない人にも必ず「いける」と伝え、理由はタイプの強みなどから作る。6タイプのタイプ名・向いている営業・求人例（イメージ表記）は今のまま表示する。ボタン「この強みで自己PRを作る」。
4. **自己PRづくり（自由回答3問）**：「熱中したことは？」「仕事で不満に思ったことは？」「その不満に、自分で何かした？」。短くてよいと案内する。答えと診断タイプをもとに、AIが自己PRを作る。
5. **出口（2つから選ぶ）**：できあがった自己PRを表示し、2つのボタンを出す。
   - **A. プロと一緒に仕上げる（無料）**：一番目立たせる。説明「求人も一緒に探せます」。
   - **B. 自分で完成させる**：履歴書・職務経歴書をダウンロード。
   - 連絡先はこの出口で初めて聞く。

### 出口A：プロと一緒に仕上げる

- 入力：呼ばれたい名前（フルネーム必須にしない）、電話番号、連絡方法（電話 / LINE）、つながりやすい時間帯、現在の職業、希望の職業（加藤さん：面談前に助かる情報）。
- 同意：「入力した内容・診断結果・自己PRを、提携先一覧に記載の人材紹介会社（BEPRIDE）に提供し、連絡を受けることに同意する」。この出口では**必須**。
- 送信後の画面：「BEPRIDE から連絡します」と表示する。LINE を選んだ人には、BEPRIDE の LINE 公式アカウントを友だち追加するボタンを表示する。
- 申し込みは Supabase に保存する。
- **届け方（最初の形・決定）**：申し込みが保存されたら、**info@kanata.careers に自動でメールを送る**。kanata が中身を確認してから BEPRIDE に渡す。BEPRIDE の希望（「BEPRIDE 側で確認すること」3）が決まったら、届け方を見直す。
  - メールにはどの申し込みかがわかる情報（申し込みID・呼ばれたい名前・電話・連絡方法・時間帯・現在／希望の職業・診断タイプ）を入れる。自己PR全文は管理画面で見る。
  - メール送信サービス（Resend などを想定）の登録と、送信用の鍵（APIキー）の環境変数への設定は、ユーザーが行う。鍵が無いときはメールを送らず、保存だけは成功させる（申し込みを取りこぼさない）。メール送信の失敗で申し込みをエラーにしない。
  - 第三者提供の記録のため、申し込みテーブルに「提供日」「提供先」の列を持たせる。kanata が BEPRIDE に渡したときに管理画面で記入する。
- 同じ人が何度申し込んでも受け付ける（重複チェックはしない）。そのかわり、今と同じレート制限をかける。
- 申し込みの取り消し・データ削除の窓口は、プライバシーポリシーに記載のお問い合わせメール（info@kanata.careers）とする。

### 出口B：自分で完成させる

- 基本情報（今の Step1 の項目：氏名・生年月日・住所・電話・メール・写真・学歴・職歴・資格・本人希望）を入力する。
- 職務経歴書用の入力（下記）を行う。
- 履歴書PDFと職務経歴書PDFをダウンロードできる。
- ダウンロード時の同意モーダル（必須：規約・ポリシー／任意：提携先から求人の案内を受け取る（デフォルトOFF）／任意：メルマガ）とアンケートは今の仕組みを使う。

## 職務経歴書（新規）

**構成**
1. **職務要約**（3〜4行、AIがまとめる）
2. **職務経歴**（勤務先ごと）：期間、お店・会社の種類、雇用形態（アルバイトも正直に「アルバイト」と書く）、主な仕事内容、頑張ったこと・うまくいったこと
3. **活かせる経験・スキル**（選択式。例：接客、クレーム対応、新人教育、レジ・売上管理）
4. **自己PR**（④で作ったもの）

**入力の負担を減らす**
- 勤務先ごとに聞くのは「何をしていたか」（選択式＋ひとこと）と「頑張ったこと・うまくいったこと」（自由回答）の2つだけ。
- ④の「熱中したこと」などの答えを使い回してよい。
- 「人数や期間など、数字があれば書いてね」と促すだけにする。

**書き方のルール**
- 盛らない。伝え方で良く見せる。
- 数字・実績は本人が書いたときだけ入れる。

## AIのルール（自己PR・職務要約・職務経歴の整文）

- 本人の回答に無い数字・実績・固有名詞を作らない（最重要。「失敗とみなすこと」に該当）。
- 本人の言葉と経験を、営業で活きる強みに言い換える。
- 今の入力の無害化処理（プロンプトインジェクション対策）とレート制限を引き継ぐ。
- 6タイプの例文（`src/data/types.ts` の `selfPR`）に入っている架空の数字は削除する。例文を AI に渡す場合は「書き方の型」として渡し、数字は真似させない。
  - 例文の書き直しは作る人が行い、できあがった文はユーザーが確認する。
- 「回答に無い数字を作らない」ことは、プロンプトのルールで指示する。あわせて、プロンプトの組み立て部分をテストで確かめる（ルールの文が入っているか、例文に数字が残っていないか）。

## データと個人情報

- 出口Aの申し込み（呼ばれたい名前・電話・連絡方法・時間帯・現在の職業・希望の職業・診断タイプ・自由回答・自己PR・同意・申込日時・流入元）を Supabase に新たに保存する。テーブル・列の追加が必要（今回は DB 変更を伴う）。
- 出口Bは今の `users` / `resumes` の保存を使う。職務経歴書の入力も `resumes.data` などに含めて保存する。
- 診断結果・自由回答・AIが作った自己PRは、出口を選ぶまで**ブラウザの中だけ**に持つ（React の状態と sessionStorage）。同意前の情報をサーバーに保存しない。
- 自由回答のテキストは、伏せ字などの加工をせずにそのまま AI（Anthropic）に送る。お店の名前などが入る可能性があることを、プライバシーポリシーに書く。氏名・電話などの連絡先は AI に送らない。
- プライバシーポリシーを更新する。対象は、取得する情報（自由回答・職務経歴・連絡方法など）、AI に送る情報、出口Aでの提携先への提供の3点。提携先一覧（`src/data/partners.ts`）・送客のルール（HANDOFF.md「送客データの扱い」）は引き継ぐ。
- `PARTNER_READY` が false（提携中の会社が0社）のときは、出口Aを表示しない。

## 今の流れの扱い

- 今の流れ（最初に基本情報を入力する4ステップ）は、新しい流れに**置き換える**。両方を並べて残さない。
- すでに保存されている `users` / `resumes` のデータはそのまま残す。データの移し替えはしない。

## 作る順番

BEPRIDE への確認（下記1）と並行して進める。受け入れNGでも作り直しが最小限で済むよう、出口Aを最後にする。

1. 診断（経験の質問・「いける！」の結果画面）
2. 自己PRづくり（自由回答3問・AIのルール・例文の書き直し）
3. 出口B（基本情報・職務経歴書の入力・職務経歴書PDF）
4. 出口A（申し込みフォーム・保存・メール通知・LINE ボタン）
5. プライバシーポリシーの更新

## 引き継ぐもの・変えないもの

- 6タイプ、10問、配点、同点時の決め方（`src/data/scoring.ts`）と、そのテスト
- 求人例（イメージ表記）、提携先一覧、運営会社の表示、利用規約
- PDF（履歴書）のレイアウト。職務経歴書PDFは新規に作る。
- 本番反映は main への push（Vercel 自動デプロイ）。push はユーザーが行う。

## BEPRIDE 側で確認すること（実装と並行してユーザーが確認）

1. 高卒・フリーター中心で正社員経験が少ない人を、面談（課金）の対象として受け入れてもらえるか。**NGなら収益の流れが成り立たないので最優先。**
2. LINE 公式アカウントの友だち追加用URL（またはQRコード）
3. 申し込みをどんな形で、どのくらいの早さで受け取りたいか（最初は kanata 経由で渡す。直接メール・スプレッドシートなどの希望があれば見直す）
4. 出口Aの申し込みが、「1面談いくら」の課金にどう数えられるか

## 作る人に任せること

- 画面の細かいデザイン・文言（ペルソナと「失敗とみなすこと」に沿っていること）
- 経験を聞く質問の正確な文言と選択肢、「いける！」の理由文のパターン
- 自由回答の入力欄の文字数上限
- DB のテーブル名・列名、職務経歴書のデータ構造
- 職務経歴書PDFのレイアウト（履歴書PDFと同じ書体・トーン）
- 既存画面（Step1〜4）をどこまで流用し、どこから作り直すか
